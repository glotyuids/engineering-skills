# PostgreSQL patterns

How a service's schema, queries and transactions are shaped so that they stay correct under
concurrency, stay fast as the tables grow, and cannot return another user's row. Written
against the MANAGED_PG capability — nothing here assumes a particular provider or a
particular application language.

Items marked `[!]` caused a real production incident when missed. They are not style
preferences.

## Scope

This skill defines only: **schema and type conventions, indexing, query shape, JSONB usage,
transactions and concurrency, connection-pool sizing, ownership enforcement, and the
diagnostic queries used to find a slow query.**

It does not define: how migration files are named, ordered, made reversible or recovered
after a failed run — that is the `database-migrations` skill in this pack. It does not
define application layering or repository interfaces; if the `go-conventions` skill (or your
language's equivalent) is installed, follow it for where a repository lives, otherwise
follow the project's own conventions. Chart wiring, DSN delivery and the migration hook Job
belong to the infra pack.

## 1. Schema conventions

| Decision | Convention | Why |
|---|---|---|
| Identifiers | `lower_snake_case`, unquoted, singular column names, plural table names (pick one and hold it repo-wide) | anything else forces quoting forever |
| Surrogate key | `bigint GENERATED ALWAYS AS IDENTITY`, or UUIDv7 when ids must be generated by the client or be non-guessable | see the UUID note below |
| Natural key | keep it as a `UNIQUE` constraint *in addition to* the surrogate PK, never as the PK | natural keys change; foreign keys then have to be rewritten |
| Text | `text`, plus a `CHECK (length(col) <= n)` when a bound is genuinely required | `varchar(n)` has no performance advantage and a length change is a table rewrite |
| Money | `numeric`, or `bigint` in integer minor units (cents, micro-units) with the unit fixed in the column name or a comment — never `float`/`double precision` | binary floats cannot represent decimal amounts; integer units make arithmetic exact and cheap, `numeric` keeps arbitrary scale — one choice per schema |
| Time | `timestamptz` **always**, never bare `timestamp` | a bare timestamp silently reinterprets on a server or session timezone change |
| Flags | `boolean`, not `smallint`/`char(1)` | |
| Enumerations | `text` + `CHECK (col IN (…))`, or a lookup table | a PostgreSQL `enum` type cannot drop a value and adding one used to be transaction-hostile |
| Nullability | `NOT NULL` by default; a nullable column must have a documented meaning for NULL | "unknown" and "not applicable" are different states |
| Foreign keys | declared, with an explicit `ON DELETE` action | an undeclared FK is an orphan-row generator |

- **Random UUIDv4 as the primary key of a large, write-heavy table** scatters inserts
  across the whole B-tree instead of appending to its right edge: write amplification, index
  bloat and a cache-hit rate that falls off as the table grows. Use `bigint IDENTITY`, or
  UUIDv7 (time-ordered) when a UUID is required for opacity or client-side generation.
- Timestamps: a table whose *database* time is the truth gets
  `created_at timestamptz NOT NULL DEFAULT now()`. Where the application injects its clock
  (deterministic tests, replayable runs) or the time is a domain fact — the moment an event
  was *accepted*, not written — the writer supplies the value and the column has **no**
  default, so a forgotten value fails on `NOT NULL` instead of being silently stamped by
  the server. Add `updated_at` only if something maintains it — a trigger or every writing
  statement. A never-updated `updated_at` is worse than none, because reports trust it.
- **Every user-owned table carries the owner column** (`user_id` or the project's
  equivalent), including join tables and append-only logs. See §7.
- Constraints belong in the database, not only in application code (`NOT NULL`, `CHECK`,
  `UNIQUE`, FK): application-only validation is bypassed by every backfill, admin script and
  one-off pod that ever touches the table.

**Soft versus hard delete.** Decide per table and write the decision down:

| Choose | When | Consequences you must accept |
|---|---|---|
| Hard delete | The row has no audit, billing or undo value | FK `ON DELETE` behaviour must be correct on every child table |
| Soft delete (`deleted_at timestamptz`) | Undo, audit or referential history matters | **Every** query must filter `deleted_at IS NULL`; unique constraints must become partial (`UNIQUE … WHERE deleted_at IS NULL`), or a re-created row collides with a deleted one; indexes should be partial on the same predicate |

Mixing the two in one schema is fine; mixing them in one table's access paths is how
"deleted" rows come back in one endpoint and not another. If soft delete is the rule, put
the filter in a view or in the single canonical repository method rather than in 40 call
sites.

**Rebuildable versus operational state.** Where projections are rebuilt from an event log,
classify every table when it is created: **source of truth** (the events — never truncated),
**rebuildable** (a projection or read model, dropped and rebuilt from the events, so nothing
lives there that the events do not contain), or **operational** (processed-update ids,
single-use nonces, outbox rows, leases, idempotency keys — facts about *delivery*, not about
the domain, that no event can regenerate). Operational rows live in their own tables, never
as columns of a projection, and the rebuild procedure names exactly which tables it
truncates. A nonce stored in a projection is re-armed by the next rebuild.

## 2. Parameterize — always

`[!]` **Every value in every statement is bound as a parameter (`$1`, `$2`, …). SQL built by
concatenating or formatting a value into the string is an injection defect, not a style
issue — flag it as a blocking finding in review even when the value "comes from our own
code".** Today's internal enum is tomorrow's query-string field.

```sql
-- BAD  — interpolated value
SELECT * FROM documents WHERE owner_id = '<interpolated>' AND status = '<interpolated>';

-- GOOD — bound parameters
SELECT id, title FROM documents WHERE owner_id = $1 AND status = $2;
```

Recurring cases and their correct form:

| Case | Correct form |
|---|---|
| Variable-length `IN` list | `WHERE id = ANY($1)` with an array parameter — not a generated `IN (…, …)` |
| Optional filter | `WHERE ($2::text IS NULL OR status = $2)`, or build the *predicate list* from a fixed set of fragments and bind their values |
| `LIKE` / `ILIKE` with user input | bind the whole pattern, and escape `%` and `_` in the user's part |
| Sort column / direction from the client | map through an explicit allowlist to a literal fragment; never interpolate the identifier |
| Genuinely dynamic identifiers (rare, admin tooling) | `format('%I', …)` / `quote_ident` — identifiers cannot be bound as parameters, so an allowlist is still the primary defence |

Only the *structure* of a query may be assembled in code (an owner predicate, a page
clause), and only from fragments the code owns. The moment a caller-supplied string reaches
the statement text, it is a finding.

## 3. Indexing

**Index these:**

- Every column in a selective `WHERE`, every `JOIN` key, and `ORDER BY` columns that are not
  already covered.
- **Every foreign key's referencing column.** PostgreSQL creates an index for the *referenced*
  side (the PK) but not the referencing side; without it, a delete or key update on the
  parent seq-scans the child table and takes a lock while doing it.
- The owner column, and usually as the *first* column of the composite indexes on that table
  (§7) — every query is scoped by it.

**Composite index column order** — the leftmost-prefix rule decides everything:

1. Equality columns first, in any order among themselves.
2. Then the `ORDER BY` columns, in the order and direction the query uses.
3. Then range columns (`<`, `>`, `BETWEEN`) last — a range stops the index being usable for
   anything to its right.

`(owner_id, status, created_at DESC)` serves `WHERE owner_id = $1 AND status = $2 ORDER BY
created_at DESC` and also `WHERE owner_id = $1`. It does not serve `WHERE status = $2`
alone. One well-ordered composite index replaces several single-column ones.

**Partial indexes** — index the rows queries actually touch:

```sql
CREATE INDEX ON documents (owner_id, created_at DESC) WHERE deleted_at IS NULL;
CREATE UNIQUE INDEX ON subscriptions (owner_id) WHERE status = 'active';  -- one active per owner
```

Smaller index, cheaper writes for excluded rows, and the unique-partial form expresses
business rules that application code cannot enforce under concurrency.

**Other kinds, and when:**

| Need | Index |
|---|---|
| JSONB containment (`@>`) | `GIN (col jsonb_path_ops)` |
| One scalar key of a JSONB column | expression B-tree: `((col ->> 'status'))` |
| Substring / `ILIKE '%x%'` search | trigram GIN (`pg_trgm`) — a plain B-tree cannot help a leading wildcard |
| Full-text search | `GIN` over a `tsvector` (generated column preferred over a trigger) |
| Index-only scans for a hot narrow query | `INCLUDE (…)` covering columns |

**An unused index is not free.** Every insert, update and delete maintains it; it consumes
cache and disk and slows `VACUUM`. Audit `idx_scan = 0` indexes (§8) and drop them. Watch
for duplicates: an index on `(a)` is redundant when `(a, b)` exists.

- An index that is never a plan's choice is usually a *shape* mismatch (wrong column order,
  a function applied to the column in the predicate, or a type mismatch forcing a cast) —
  fix the shape rather than adding a second index.
- Creating an index on a live table takes a write-blocking lock unless created concurrently;
  the mechanics and the failure modes of that belong to `database-migrations`.

## 4. Query patterns

**The N+1 pattern** — one query for a list, then one query per row:

```
rows = SELECT id, … FROM parents WHERE owner_id = $1     -- 1
for each row: SELECT … FROM children WHERE parent_id = $1 -- N
```

How to spot it: a query inside a loop, a "load the details" helper called from a mapper, an
ORM/association access inside a serializer, or a request whose latency scales linearly with
the number of items returned. In logs, it shows as the same statement repeated with
different parameters in one request id.

Fixes, in order of preference: one `JOIN`; one second query with `WHERE parent_id = ANY($1)`
grouped in memory; a `LATERAL` join when only the top *k* children per parent are needed.
The same rule applies to writes — batch inserts as one multi-row `INSERT` (or `COPY` for
bulk loads), never one statement per element.

**Pagination.** `OFFSET n` makes the database read and discard *n* rows on every page: page
1000 costs 1000 pages of work, and a concurrent insert shifts the window so rows are skipped
or repeated. Use keyset (seek) pagination on an indexed, unique-tie-broken sort key:

```sql
SELECT id, created_at, …
FROM documents
WHERE owner_id = $1 AND (created_at, id) < ($2, $3)   -- last row of the previous page
ORDER BY created_at DESC, id DESC
LIMIT $4;
```

`OFFSET` is acceptable only for small, bounded result sets (an admin screen over hundreds of
rows). If the product requires jump-to-page over a large table, that is a product decision
with a known cost — say so.

**Other query rules:**

- No `SELECT *` in application code. It breaks when a column is added, transfers columns
  nobody reads, and defeats index-only scans.
- Never fetch a whole table and filter, sort, aggregate or paginate in application memory.
  `COUNT`, `SUM`, `DISTINCT`, `GROUP BY` and `LIMIT` belong in SQL.
- Prefer `EXISTS (SELECT 1 …)` over `COUNT(*) > 0`; it stops at the first match.
- An exact `COUNT(*)` over a large table is a full scan. For "about how many", use the
  planner's estimate from `pg_class.reltuples` and label it as approximate.
- Avoid functions on indexed columns in predicates (`WHERE lower(email) = $1` needs an
  expression index on `lower(email)`; `WHERE date(created_at) = $1` needs a range predicate
  instead).
- Use `INSERT … ON CONFLICT` for upserts rather than select-then-insert, which races.
- `RETURNING` gives you the written row without a second round trip.
- **Run `EXPLAIN (ANALYZE, BUFFERS)` before a query ships when it sits on a request path,
  runs per row or per job, or touches a table that will grow.** Flag sequential scans on
  large tables, row estimates off by an order of magnitude from actuals (stale statistics,
  or a predicate the planner cannot estimate), and nested loops over large inputs. Run it
  against realistic data volumes — every plan is index-free on 50 rows. A low-volume
  internal table (an owner directory, a settings row) does not need a plan per query;
  review its plan when a query changes shape or the table's growth assumption changes.

## 5. JSONB and its limits

JSONB is right for: genuinely schemaless payloads (a webhook body kept verbatim), sparse
per-record attributes with no cross-record queries, versioned document snapshots, and
denormalised read models. It is wrong as a way to avoid designing a schema: a field that is
filtered, sorted, joined or constrained wants a column, where the type system, `NOT NULL`
and `CHECK` still apply.

`[!]` **JSONB operators and set-returning functions fail at runtime on a NULL or scalar
value.** A single bad row aborts the whole statement — and in a migration or a backfill, the
whole run. Guard the type before applying the operator:

```sql
-- BAD: errors as soon as one row holds NULL or a non-array value
SELECT jsonb_array_elements_text(tags) FROM documents;

-- GOOD: coerce anything that is not an array to an empty array first
SELECT jsonb_array_elements_text(
    CASE WHEN jsonb_typeof(tags) = 'array' THEN tags ELSE '[]'::jsonb END
) FROM documents;
```

The same guard applies to `jsonb_each`, `jsonb_object_keys`, `jsonb_array_length` and to
`->>` chains that assume an object. `COALESCE(col, '{}'::jsonb)` handles the NULL half only —
it does not save you from a scalar or an unexpected type.

Further rules:

- Prefer `NOT NULL DEFAULT '{}'::jsonb` (or `'[]'`) over a nullable JSONB column: it removes
  the NULL branch of every guard above.
- Add a `CHECK (jsonb_typeof(col) = 'object')` when the column is contractually an object.
- Index for the access pattern: `GIN (col jsonb_path_ops)` for `@>` containment, a B-tree
  expression index for one extracted key. An unindexed JSONB predicate is a full scan plus
  per-row parsing.
- Updating one key rewrites the whole value (MVCC copies the row). Large JSONB documents
  updated frequently are a write-amplification problem; they are also TOASTed, so reads pay
  a detoast cost.
- Version the shape inside the document (`"v": 2`) and make readers tolerate both versions —
  a JSONB column has no migration story of its own.

## 6. Transactions, locking and the connection pool

**Transaction discipline:**

1. **Keep them short.** A transaction holds its locks and pins the oldest snapshot until it
   commits; a long one blocks `VACUUM` from cleaning dead tuples database-wide.
2. **Always arrange the rollback the moment the transaction is opened**, on every path — a
   deferred call, a context manager, or a helper that owns begin/commit/rollback. After a
   successful commit the rollback is a harmless no-op; without it, an early return, an
   exception or a panic leaks the connection and holds its locks until the pool times out.
3. `[!]` **Never hold a transaction open across a network call** — an HTTP request, a model
   provider call, a broker publish, an object-storage upload. The remote side's slowest day
   becomes your lock-hold time and your pool exhaustion. Write the state, commit, then call
   out; if the two must be atomic in effect, use the outbox pattern (commit the intent in the
   same transaction as the state change, deliver it asynchronously).
4. One canonical transaction helper per service, reused. Hand-rolled begin/commit/rollback in
   every repository is where the missing rollback eventually appears.
5. Do not `BEGIN` for a single statement — it is already atomic.
6. Read-modify-write in application code is a lost-update race. Do it in one statement
   (`UPDATE … SET n = n + $1`), or lock the row with `SELECT … FOR UPDATE` inside the
   transaction, or use an optimistic `version` column and retry on zero rows affected.

**Deadlocks and lock ordering.** A deadlock needs two transactions taking the same locks in
different orders. Take row locks in a deterministic order — `SELECT … WHERE id = ANY($1)
ORDER BY id FOR UPDATE` — in every code path that locks more than one row of a table.
PostgreSQL detects the cycle and kills one transaction; the loser must be retried, so
deadlock-retry is application work, not something the database solves for you.

**Work queues in the database** — the correct claim pattern:

```sql
UPDATE jobs SET status = 'running', started_at = now()
WHERE id = (
    SELECT id FROM jobs
    WHERE status = 'queued' AND run_after <= now()
    ORDER BY run_after
    FOR UPDATE SKIP LOCKED
    LIMIT $1
)
RETURNING id, payload;
```

`SKIP LOCKED` is what lets N workers claim disjoint rows without serialising on each other.
Without it, every worker queues behind the first. Pair it with a visibility timeout (a
`running` row whose `started_at` is older than the timeout is reclaimable) and idempotent
handlers, because a worker can die after claiming.

`SKIP LOCKED` buys parallelism only across independent rows. A design that keeps a
**gapless per-owner sequence** — an event store or outbox numbering each owner's entries
consecutively, or a per-owner control row that every write locks first — has already
serialised that owner's writers. `SKIP LOCKED` then matters across owners (N workers on N
owners) and does nothing within one; say which case you are in, so nobody adds a queue to
"parallelise" writes the sequence forbids.

**Isolation levels.** `READ COMMITTED` (the default) is right for almost everything.
`REPEATABLE READ` or `SERIALIZABLE` for multi-statement invariants — but both can abort a
transaction with a serialization failure, so any code using them must have a bounded retry
loop. Advisory locks (`pg_advisory_xact_lock`) are the tool for "only one instance runs this
job", not a table row you `UPDATE`.

**Connection pool sizing.** MANAGED_PG enforces a hard connection limit, and part of it is
reserved for superuser and maintenance sessions. Exceeding it does not degrade — new
connections are refused, so the *next* service to start fails while the healthy ones keep
running, which makes the cause look unrelated.

- Budget every consumer of the same instance: `maxReplicas × pool_max` for each service (the
  autoscaling ceiling, not today's replica count), plus migration Jobs, one-off debug pods,
  the operator's own client and anything outside the cluster. The total fits with headroom.
- Small pools are correct. A pool larger than the database's useful concurrency
  (roughly a small multiple of its CPU count, shared across all services) adds queueing
  inside PostgreSQL instead of removing it. Single-digit `pool_max` per replica is a sane
  starting point; raise it from measurements, not from a timeout.
- Set a maximum connection lifetime and idle timeout so connections rotate (this is also
  what lets a failover or a rotated password take effect), and an acquire timeout so a
  starved pool surfaces as a fast, explicit error instead of a hung request.
- If a connection *pooler* sits in front of the instance (a separate port), it is usually in
  transaction-pooling mode: server-side prepared statements and session-level `SET` do not
  survive between statements. Disable statement caching in the driver, or connect to the
  direct port, and use `SET LOCAL` / `set_config(…, true)` exclusively (§7).
- `[!]` Some providers require the application driver to read a **CA certificate file** named
  in the DSN, while the driver used by the migration tool is satisfied by TLS mode alone.
  Migrations then succeed and the service crash-loops on start. The certificate's source and
  the per-driver differences are a Vendor delta — see the `skills/cloud/<vendor>` skill and,
  for mounting it, the infra pack.

## 7. Ownership: nobody reads a row they do not own

Two mechanisms enforce this. They are not alternatives — a service holding user data uses
both, because either one alone has failed in production.

**A. Repository-level scoping (application layer).**

- Every repository method takes the authenticated subject as an explicit parameter. A method
  that *can* be called without one will eventually be called without one.
- The owner predicate is added to **every** read and **every** write, including updates,
  deletes, counts, aggregates and internal endpoints. "Internal" is not "unscoped".
- `[!]` **Never trust an owner id supplied by the client** — body, query string, header or
  path. It comes from the verified token claims, built once at the transport boundary.
- `[!]` **A row the caller does not own must be indistinguishable from a row that does not
  exist.** Both map to not-found; never "forbidden", never a different error body, never a
  different latency profile. `403` on someone else's id confirms that the id exists.

**B. Row-level security (database layer).** The policy compares the owner column against a
session setting that the application sets from the subject at the start of each transaction:

```sql
ALTER TABLE <table> ENABLE ROW LEVEL SECURITY;
ALTER TABLE <table> FORCE  ROW LEVEL SECURITY;
CREATE POLICY <table>_owner_isolation ON <table>
  USING      (owner_id = NULLIF(current_setting('app.owner_id', true), '')::uuid)
  WITH CHECK (owner_id = NULLIF(current_setting('app.owner_id', true), '')::uuid);
```

- `USING` filters what is visible to reads, updates and deletes; `WITH CHECK` validates what
  writes produce. **A policy with only `USING` lets a caller insert rows owned by someone
  else.**
- `FORCE ROW LEVEL SECURITY` matters: without it the table's *owner* role — often the same
  role the application connects as — bypasses its own policies entirely and the isolation is
  decorative. Roles with `BYPASSRLS` and superusers bypass it regardless.
- The second argument `true` to `current_setting` means "missing is not an error"; `NULLIF(…,
  '')` turns the unset case into NULL, and `owner_id = NULL` matches no rows. So a code path
  that forgets to set the variable reads **zero rows** rather than everything — a safe
  failure, but a confusing one. Put it first in the failure-modes list (§9).
- Set the variable inside the transaction, scoped to it. `SET LOCAL` cannot take a bind
  parameter, so set it through `set_config` with the local flag:

```sql
BEGIN;
SELECT set_config('app.owner_id', $1, true);   -- true = transaction-local
-- … the scoped statements …
COMMIT;
```

  `[!]` A session-level `SET` (without the local flag) on a pooled connection outlives the
  request and hands the previous caller's identity to the next one. Transaction-local, every
  time.
- The transaction-with-setting helper is written **once** per service and reused; every
  repository method runs inside it.
- Enable the policy in the table's **creating** migration. Retrofitting isolation later means
  auditing every query written in between, and every row already inserted.
- Index the owner column and lead composite indexes with it — the policy adds its predicate
  to every query, so an unindexed owner column makes every scoped read a scan.

**Enumerating owners under `FORCE`.** A forced policy binds the table owner too, and a
`SECURITY DEFINER` function owned by the table owner runs *as* that owner, so it is bound
as well — it is not a back door. A system task that must see every owner (a scheduler, a
sweeper, a per-owner backfill) therefore reads a small **directory table without row
security** — one row per owner, ids only, no owner content — and then does its work inside
the normal per-owner transaction. Fallbacks, in order: a dedicated maintenance role with
`BYPASSRLS` used by that task alone and never by the application; or setting the session
variable per owner in a loop. Never drop `FORCE` to make enumeration convenient.

**Verify before claiming defence in depth.** If the RLS migration has not shipped, the
application predicate is the *only* guard; say that plainly rather than describing two
layers. The proof is a test, not a review: with two subjects and one row, the second subject
gets not-found from every method — read, update, delete, list and count.

## 8. Diagnostics

The queries that find the slowest statements, the biggest tables, indexes nobody uses,
long-open transactions, blocking sessions, the connection budget and autovacuum debt are
collected in [`references/diagnostics.md`](references/diagnostics.md). Two prerequisites:
`pg_stat_statements` must be enabled on the instance — on MANAGED_PG usually an instance
setting, not a superuser `CREATE EXTENSION` you can run yourself — and the session you use
is read-only.

Then take the offending statement and run `EXPLAIN (ANALYZE, BUFFERS)` on it with
production-like parameters. Read the plan bottom-up; compare estimated versus actual rows
at each node.

## 9. Failure modes

| Symptom | Likely cause | Fix |
|---|---|---|
| A scoped query returns zero rows in production, works in tests | the transaction-local owner setting was never set on this path, so the RLS predicate compares against NULL | run the query through the canonical transaction helper (§7) |
| A user sees another user's data after a burst of traffic | session-level `SET` on a pooled connection leaked the previous request's identity | transaction-local `set_config` only (§7) |
| Inserts succeed with someone else's owner id | policy declares `USING` but no `WITH CHECK` | add `WITH CHECK` (§7) |
| RLS "enabled" but everything is visible | policy not `FORCE`d and the app connects as the table owner, or the role has `BYPASSRLS` | `FORCE ROW LEVEL SECURITY`, connect as a non-owner role |
| A system task under forced row security sees zero owners | it ran under the policy with no owner set, and there is no owner directory | read a directory table without row security, then work per owner (§7) |
| Endpoint latency grows linearly with page size | N+1 | join, or one `= ANY($1)` batch (§4) |
| Page 500 is slow, rows repeat or vanish between pages | `OFFSET` pagination | keyset pagination (§4) |
| Statement aborts with a JSONB type error, and a migration rolls back whole | operator applied to NULL or a scalar | `jsonb_typeof` guard (§5) |
| `too many connections` on deploy, unrelated service fails to start | pool budget exceeds the instance limit; autoscaling multiplied it | size against `maxReplicas × pool_max` plus Jobs and one-off pods (§6) |
| Requests hang, then time out in the pool | a transaction held open across a network call, or a missing rollback | commit before calling out; deferred rollback on every path (§6) |
| Deadlock errors under concurrency | two paths lock the same rows in different orders | deterministic `ORDER BY id … FOR UPDATE`, plus retry (§6) |
| Queue workers process the same job twice, or serialise behind each other | claim without `FOR UPDATE SKIP LOCKED`, or no visibility timeout | the claim pattern in §6 |
| Table keeps growing after deletes; scans stay slow | a long-running transaction blocks `VACUUM` from reclaiming dead tuples | find and end it (§8) |
| A plan ignores the obvious index | wrong column order, a function or a cast on the indexed column, or stale statistics | reshape the predicate or the index; `ANALYZE` (§3) |
| Writes got slower after a feature shipped, reads unchanged | indexes added for a query that never uses them | drop unused indexes (§3, §8) |
| Deleting a parent row takes minutes and locks the child table | no index on the referencing FK column | index it (§3) |
| The service crash-loops on start with a certificate error while migrations succeeded | driver asymmetry on MANAGED_PG TLS | mount the CA file for the app; see the vendor skill (§6) |

## 10. Definition of done

- [ ] Every statement's values are bound parameters; no caller-supplied string reaches
      statement text.
- [ ] Types follow §1: `timestamptz`, `numeric` or integer minor units for money, `text`,
      explicit `NOT NULL`, declared FKs with an `ON DELETE` action.
- [ ] Every user-owned table carries the owner column; it is indexed and leads the composite
      indexes.
- [ ] Every FK's referencing column is indexed; composite index order matches the query's
      equality-then-order-then-range shape.
- [ ] Soft-deleted tables filter `deleted_at IS NULL` in every access path, with partial
      unique constraints.
- [ ] `EXPLAIN (ANALYZE, BUFFERS)` run on every new query on a request path or a growing
      table, against realistic volumes; no unexplained sequential scan on a large table.
- [ ] No query inside a loop; list endpoints paginate by keyset; no `SELECT *`.
- [ ] JSONB operators are type-guarded; JSONB predicates that run in production are indexed.
- [ ] Transactions are short, have a deferred rollback on every path, and contain no network
      call.
- [ ] Multi-row locking uses a deterministic order; queue claims use `FOR UPDATE SKIP LOCKED`.
- [ ] Pool size budgeted against the MANAGED_PG connection limit at maximum replica count.
- [ ] Ownership is enforced in the repository *and* by policy, the owner value comes from
      verified claims, and a test proves a second subject gets not-found from every method.
